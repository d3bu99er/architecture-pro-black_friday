# Принятый подход

В рамках анализа было выявлено, что перенос ключевых транзакционных сущностей системы требует осторожного подхода.

Критически важным бизнес-инвариантом системы является атомарность операции:

**создание заказа → обновление остатков товара.**

Если эти операции выполняются в разных хранилищах без транзакционной гарантии, появляется риск продажи товаров, которые фактически уже закончились.

По этой причине было принято решение:

**не переносить транзакционные сущности `Orders` и `Products` из MongoDB.**

Они остаются в текущем хранилище, где могут обрабатываться в рамках транзакционной логики.

Cassandra используется для хранения данных, которые:

- создают значительную нагрузку на запись,
- не требуют строгой транзакционной согласованности,
- допускают eventual consistency.

---

# Почему Cassandra

Основные свойства Cassandra, релевантные задаче:

* высокая производительность записи;
* горизонтальное масштабирование без глобальной миграции данных;
* встроенная отказоустойчивость;
* равномерное распределение данных благодаря consistent hashing.

Эти свойства делают Cassandra подходящей для хранения высоконагруженных потоков данных, не требующих строгих транзакционных гарантий.

# Обоснование переноса

## Почему не переносится Orders

Создание заказа всегда сопровождается обновлением остатков товаров.

Если заказ создаётся в одной базе данных, а остатки обновляются в другой, то между операциями возникает временное окно, в котором:

* сервис может увидеть устаревшее состояние остатков,
* возможно создание заказа на уже отсутствующий товар.

Для предотвращения таких ситуаций операции должны выполняться в рамках транзакции.

Поэтому **контур заказа (`Orders` + остатки `Products`) остаётся в MongoDB**.

---

## Какие данные переносятся в Cassandra

В Cassandra переносятся данные, не участвующие в транзакционных операциях:

### ProductReminders

Сервис напоминаний о товарах выполняет:

* массовые записи событий,
* периодические фоновые обработки,
* рассылку уведомлений.

Данные такого типа:

* write-heavy,
* допускают eventual consistency,
* хорошо масштабируются в Cassandra.

# Микросервисная архитектура

Архитектура системы остаётся распределённой и использует асинхронное взаимодействие сервисов.

Основные компоненты:

* **MongoDB**
  * транзакционный контур заказов
  * управление остатками товаров

* **Cassandra**
  * хранение напоминаний о товарах
  * обработка фоновых событий

* **Kafka**
  * обмен событиями между сервисами

* **Celery**
  * обработка фоновых задач

# Модель данных Cassandra

### Таблица ProductReminders

Назначение таблицы - хранение запросов пользователей на уведомление о появлении товара.

#### Partition Key

```

product_id

```

Это позволяет эффективно получать список пользователей, ожидающих появление конкретного товара.

#### Clustering Columns

```

created_at

````

Позволяет хранить напоминания в хронологическом порядке.

---

## Пример CQL

```sql
CREATE TABLE ProductReminders (
    product_id uuid,
    user_id uuid,
    created_at timestamp,
    notification_type text,
    status text,
    PRIMARY KEY ((product_id), created_at, user_id)
);
````

# Обработка отказов

### 1. Недоступность Cassandra

Фоновый сервис повторяет запись через механизм ретраев.

### 2. Потеря сообщения в брокере

Используется механизм гарантированной доставки сообщений.

### 3. Временная рассинхронизация данных

Допускается модель eventual consistency, так как данные не участвуют в транзакционных операциях.

# Рассмотренные альтернативы

### Полный перенос `Orders` в Cassandra

Данный вариант был рассмотрен, но отклонён.

Причина - невозможность обеспечить строгую транзакционную согласованность между созданием заказа и обновлением остатков товаров.

---

### Перенос `Orders` и `Products` вместе

Теоретически возможно, однако потребует полной переработки транзакционной логики и усложнит архитектуру системы.
