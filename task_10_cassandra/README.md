## Принятый подход

Решение опирается на ранее утверждённую структуру данных (ADR), включая идею выделения `ProductReminders` в отдельную таблицу. Это важно для корректного разделения ответственности между хранилищами.

---

## Почему Cassandra

Основные свойства Cassandra, релевантные задаче:

* Высокая скорость записи (оптимизация под append-модель).
* Горизонтальное масштабирование без глобальной миграции данных.
* Отказоустойчивость на уровне архитектуры.
* Равномерное распределение данных благодаря consistent hashing.

## Оценка пиковых нагрузок

| Таблица          | Чтение  | Создание | Обновление | Комментарий                                           |
| ---------------- | ------- | -------- | ---------- | ----------------------------------------------------- |
| Users            | Среднее | Низкое   | Низкое     | Основная активность — у существующих пользователей    |
| Carts            | Высокое | Низкое   | Высокое    | Интенсивное изменение содержимого корзины             |
| Orders           | Высокое | Высокое  | Среднее    | Массовое создание заказов и их последующий мониторинг |
| Products         | Высокое | Низкое   | Низкое     | Поиск доминирует над изменениями                      |
| ProductReminders | Высокое | Низкое   | Высокое    | Запись при создании заказов                           |

Ключевая проблема текущей архитектуры: при добавлении новых шардов MongoDB выполняла масштабное перераспределение данных, что в период пиковых нагрузок приводило к существенному росту задержек.

Основной источник роста данных — массовое создание новых заказов. Следовательно, именно `Orders` являются триггером перегрузки и миграций.

## Обоснование переноса

### Почему переносится Orders

* Высокая интенсивность вставок.
* Прямое влияние на автомасштабирование.
* Cassandra не требует полного перераспределения данных при добавлении узлов.

### Почему остальные таблицы остаются в MongoDB

* Их нагрузка либо умеренная (`Users`),
* либо преимущественно чтение (`Products`),
* либо не является основным источником миграций (`Carts`, `ProductReminders`).

Их перенос может быть рассмотрен отдельно, если потребуется дополнительная разгрузка MongoDB.

---

## Межсервисная транзакционность

Предполагается микросервисная архитектура с разделением хранилищ. Перенос `Orders` в Cassandra создаёт межсервисные транзакции.

Для координации предлагается использовать паттерн **Saga**.

### Компоненты реализации:

* Брокер сообщений (Kafka) — обмен событиями.
* Очередь фоновых задач (Celery) — контроль завершения бизнес-процесса.
* WebSocket — асинхронное уведомление клиента о статусе заказа.

## Обработка отказов (corner cases)

1. Не удалось создать заказ в Cassandra
   → Ошибка возвращается вызывающему сервису, операция списания остатков не выполняется.

2. Не удалось обновить остатки в MongoDB
   → Фоновый процесс инициирует компенсационную операцию: отмена заказа в Cassandra и уведомление клиента.

3. Недоступность брокера сообщений
   → Компенсационный сценарий аналогичен предыдущему.

4. Сбой фонового процессора
   → Обрабатывается после восстановления через механизм повторной обработки.

## Модель данных Cassandra

### Таблица Orders

**Partition Key:** `(location, order_id)`

* Заказы одного региона логически группируются.
* Добавление `order_id` предотвращает hotspot-эффект в густонаселённых регионах.

**Clustering Columns:** `(user_id, created_at)`

* Позволяют эффективно извлекать историю заказов пользователя в хронологическом порядке.

**Модель согласованности:**

* Hinted Handoff для кратковременных сбоев.
* Anti-Entropy Repair при длительных рассинхронизациях.

### Пример CQL

```sql
CREATE TABLE Orders (
    id uuid,
    user_id uuid,
    location text,
    created_at timestamp,
    products map<uuid, int>,
    status text,
    total decimal,
    PRIMARY KEY ((location, id), user_id, created_at)
);
```

## Рассмотренные альтернативы

1. Перенос только `Products`
   Частично снижает нагрузку на MongoDB, но не устраняет первопричину задержек.

2. Перенос `Orders` и `ProductReminders`
   Даст более сильную разгрузку, но потребует программной реализации транзакционной целостности (например, transactional outbox или event sourcing).

## Ограничения и риски

### Недостатки

* Повышенная архитектурная сложность.
* Асинхронный характер создания заказа требует поддержки пользовательской сессии до завершения операции.

### Риски

* Дополнительная задержка при межсервисном взаимодействии.
* Потенциальная потеря консистентности при сбоях в распределённых транзакциях.
