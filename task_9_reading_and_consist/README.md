## Предлагаемый подход

Для выбора узла чтения используется терминология MongoDB (режимы read preference):

* **Primary**
* **Primary Preferred**
* **Secondary**
* **Secondary Preferred**
* **Nearest**

Операции, напрямую участвующие во взаимодействии с пользователем и влияющие на пользовательский опыт, далее обозначаются как **Low-Latency Interactions (LLI)**. Для них критичны минимальная задержка и высокая актуальность данных.

## Стратегии чтения по коллекциям

### Orders

| Операция               | Режим чтения        | Допустимая задержка репликации | Обоснование                                                                                                      |
| ---------------------- | ------------------- | ------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| История заказов        | Secondary Preferred | до 3 секунд                    | Допустима небольшая задержка, операция не должна нагружать primary, который обслуживает транзакционные изменения |
| Состав / статус заказа | Primary             | до 1 секунды                   | Операция относится к LLI, требуется максимальная актуальность данных                                             |

### Products

| Операция                  | Режим чтения        | Допустимая задержка репликации | Обоснование                                                                                                                  |
| ------------------------- | ------------------- | ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| Поиск по категории и цене | Secondary Preferred | до 3 секунд                    | Primary задействован в обновлении остатков. Актуальность важна (предотвращение overselling), но допустима небольшая задержка |
| Просмотр описания товара  | Secondary Preferred | до 10 секунд                   | Описания изменяются редко. Критична скорость отклика, но допустима значительная задержка данных                              |

## Итоговая логика распределения

1. Все операции, связанные с изменением состояния (заказы, корзины, остатки), обслуживаются через **primary** для обеспечения строгой консистентности.
2. Чтения, допускающие небольшую задержку, выполняются через **secondary preferred**, что снижает нагрузку на primary.
3. Для операций, входящих в LLI, приоритетом является минимальная задержка и предсказуемость отклика, даже при увеличении нагрузки на основной узел.
4. Secondary-реплики выполняют двойную роль: разгрузка primary и обеспечение отказоустойчивости.
