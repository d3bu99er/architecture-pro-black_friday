## Нефункциональные требования

| №     | Требование                                                          | Пояснение                                                            |
| ----- | ------------------------------------------------------------------- | -------------------------------------------------------------------- |
|       | **Надёжность (Reliability)**                                        |                                                                      |
| R1.1  | Равномерное потребление памяти шардами                              | Дисбаланс увеличивает вероятность отказа (например, OOM)             |
| R2.1  | Равномерное распределение запросов                                  | Перегруз отдельных шардов повышает вероятность отказа в обслуживании |
| R3.1  | Равномерная загрузка CPU                                            | Избыточная нагрузка на отдельные шарды снижает устойчивость системы  |
|       | **Ограничения (Restrictions)**                                      |                                                                      |
| R+1.1 | Использование памяти каждым шардом не превышает установленный лимит | Превышение приводит к аварийному завершению процессов                |
| R+2.1 | Загрузка CPU не выходит за пределы допустимых значений              | Перегруз повышает риск деградации сервиса                            |

## Предлагаемое решение

### Контролируемые метрики

Для оценки состояния шардов используются следующие показатели:

* **shard_volume** — объём используемой памяти;
* **shard_reqs** — количество запросов к шардy;
* **shard_cpu** — затраты процессорного времени на обработку запросов.

### Обоснование выбора метрик

* **shard_volume** позволяет контролировать как абсолютное потребление памяти, так и равномерность распределения данных.
* **shard_reqs** обеспечивает оперативное выявление всплесков нагрузки. Этот показатель важен, поскольку сбор статистики по CPU требует времени, в течение которого может произойти деградация сервиса.
* **shard_cpu** используется для фильтрации ложных тревог, когда наблюдается большое количество «лёгких» запросов. Формат представления (время выполнения за период либо доля от общей загрузки) выбирается исходя из архитектурных решений.

# Получение метрик состояния шардов

## 1. Потребление памяти

Информацию о фактическом использовании памяти шардом можно извлечь через `serverStatus()` в MongoDB.

```javascript
const shardConn = new Mongo("<shard_host>:<shard_port>");
const shardDB = shardConn.getDB("<db_name>");
const status = shardDB.serverStatus();

const shard_volume = status.mem.resident;
```

Значение `shard_volume` отражает объём физической памяти, занятой процессом шарда (в байтах).

---

## 2. Количество выполненных операций

Общая нагрузка по операциям определяется суммированием счётчиков из раздела `opcounters`.

```javascript
const shardConn = new Mongo("<shard_host>:<shard_port>");
const shardDB = shardConn.getDB("<db_name>");
const status = shardDB.serverStatus();

var shard_reqs = status.opcounters.command +
    status.opcounters.query +
    status.opcounters.update +
    status.opcounters.delete +
    status.opcounters.insert;
```

Переменная `shard_reqs` показывает суммарное число операций различных типов, обработанных данным шардом.

---

## 3. Загрузка процессора

В стандартном API MongoDB отсутствует прямой и удобный способ получения агрегированной метрики потребления CPU на уровне шарда.

При использовании контейнеризации (например, Docker) загрузку процессора можно определить на уровне контейнера:

```bash
docker stats --format "{{.Name}}: {{.CPUPerc}}" <shard1> <shard2>
```

Собранные данные позволяют вычислить относительную и абсолютную нагрузку на каждый шард.

## Критерии признания шарда перегруженным

### 1. Память

1.1. Значение **shard_volume** превышает порог Th₁ (примерно 90% доступного объёма).
1.2. Разница потребления памяти между шардами превышает X₁ (примерно 30%).

### 2. Интенсивность запросов

2.1. Значение **shard_reqs** отличается между шардами более чем на X₂ (примерно 50% с учётом возможных burst-нагрузок).

### 3. Вычислительная нагрузка

3.1. Значение **shard_cpu** превышает порог Th₂ (примерно 80%).
3.2. Разница по загрузке CPU между шардами превышает X₃ (примерно 30%).

---

## Логика критериев

* Критерии по памяти направлены на предотвращение превышения лимитов и устранение дисбаланса хранения данных.
* Критерий по количеству запросов позволяет быстро обнаружить потенциальную перегрузку и должен анализироваться совместно с CPU-показателями.
* Критерии по CPU обеспечивают контроль фактической вычислительной нагрузки и применяются совместно с метрикой запросов для исключения ложных срабатываний.

## Автоматическая балансировка

MongoDB содержит встроенный механизм балансировки, который перераспределяет чанки между шардами для поддержания равномерного распределения данных.

### Управление балансировщиком

```javascript
sh.startBalancer();  // альтернативно: sh.setBalancerState(true)

// Проверочные команды
sh.getBalancerState();   // возвращает true, если балансировщик включен
sh.isBalancerRunning();  // возвращает true, если процесс балансировки активен
```

Балансировщик автоматически переносит чанки при выявлении дисбаланса, минимизируя необходимость ручного вмешательства.

---

## Zoned Tag Sharding

Механизм зон (тегов) позволяет закреплять диапазоны ключей шардирования за конкретными шардами. Это эффективно для изначального проектирования схемы распределения данных, однако для уже существующих наборов данных может потребоваться дополнительная миграция и возможна временная избыточность размещения.

### Назначение тегов шардам

```javascript
sh.addShardTag("<shard1_name>", "<tag1>");
sh.addShardTag("<shard2_name>", "<tag2>");
```

### Закрепление диапазонов ключей за зонами

```javascript
sh.addTagRange(
  "<db_name>.<collection>",
  {"<shard_key>": "<range1_min>"},
  {"<shard_key>": "<range1_max>"},
  "<tag1>"
);

sh.addTagRange(
  "<db_name>.<collection>",
  {"<shard_key>": "<range2_min>"},
  {"<shard_key>": "<range2_max>"},
  "<tag2>"
);
```

### Проверка распределения

После вставки данных:

```javascript
for (var i = 0; i < 1000; i++)
  db.collection.insert({/* document */});

db.helloDoc.getShardDistribution();
```

### Расширение диапазонов

При росте объёма данных диапазоны можно дополнить:

```javascript
sh.updateZoneKeyRange(
  "<db_name>.<collection>",
  {"<shard_key>": "<range3_min>"},
  {"<shard_key>": "<range3_max>"},
  "<tag1>"
);
```

### Добавление нового шарда с выделением зоны

```javascript
sh.addShard("<new_shard_name>/<new_shard_host>:<new_shard_port>");
sh.addShardTag("<new_shard_name>", "<new_shard_tag>");

sh.addTagRange(
  "<db_name>.<collection>",
  {"<shard_key>": "<new_range_min>"},
  {"<shard_key>": "<new_range_max>"},
  "<new_shard_tag>"
);
```

После вставки новых данных распределение будет происходить в соответствии с назначенными зонами.

## Ручное перераспределение

Когда автоматическая балансировка не обеспечивает требуемый результат (например, при наличии «горячих» ключей), используются ручные методы управления чанками.

### Перемещение чанка на конкретный шард

```javascript
sh.moveChunk(
  "<db_name>.<collection>",
  { shard_key_field: <value> },
  "target-shard-name"
);
```

---

### Принудительное разделение чанка

```javascript
sh.splitAt("<db_name>.<collection>", { shard_key_field: "<hash_value>" });
sh.splitAt("<db_name>.<collection>", { shard_key_field: "<hash_value2>" });
```

Дробление чанков позволяет повысить гранулярность балансировки.

---

### Добавление нового шарда

```javascript
sh.addShard("<name>/<host>:<port>");
```

После подключения нового узла балансировщик автоматически перераспределит часть данных.

---

### Изменение размера чанка

Уменьшение размера чанков делает автобалансировку более чувствительной и частой:

```javascript
db.settings.updateOne(
  { _id: "chunksize" },
  { $set: { value: 64 } },  // по умолчанию 128MB
  { upsert: true }
);
```

---

### Расширение ключа шардирования

Если текущий ключ недостаточно селективен, его можно дополнить:

```javascript
db.adminCommand({
  refineCollectionShardKey: "<db_name>.<collection>",
  key: { current_shard_key_field: 1, additional_shard_key_field: 1 }
});
```

Это увеличивает гранулярность распределения без полной перешардировки.

---

### Полная смена ключа шардирования

При системной проблеме с текущим ключом выполняется перешардирование:

```javascript
db.adminCommand({
  reshardCollection: "<db_name>.<collection>",
  key: { new_shard_key_field: "<hash_type>" }
});
```

Данная операция является ресурсоёмкой и требует предварительной оценки рисков, так как приводит к масштабной миграции данных внутри кластера.
</details>

### Подход к выбору механизма балансировки

1. **Стратегический уровень**
   Для минимизации динамических миграций рекомендуется заранее определить стратегию шардирования, включая использование механизма Zoned Tag Sharding.

2. **Нарушение критерия 1.1 (превышение лимита памяти)**
   Требуется увеличение числа шардов либо расширение ресурсных лимитов кластера.

3. **Нарушение критерия 1.2 (дисбаланс объёма данных)**
   Рекомендуется включение или корректировка автоматической балансировки MongoDB.

4. **Нарушение критериев 2.1, 3.1 или 3.2**
   Если автоматическая балансировка не устраняет проблему, необходимо:

   * провести анализ распределения ключей;
   * выявить «горячие» данные;
   * выполнить целевую ручную миграцию.

В подобных ситуациях данные могут быть распределены формально равномерно, однако отдельные ключи обладают повышенной популярностью (частые запросы) либо участвуют в ресурсоёмких операциях. В этих случаях стандартный алгоритм балансировки MongoDB не обеспечивает оптимального результата.
